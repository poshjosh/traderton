**Status:** PLAN (not yet implemented)
**Repos / branches:** traderton `l3-integration` · herobids `consume-traderton`
**Law:** COPY, NEVER AUTHOR trading behaviour. The only authored things here are
DELETIONS (the dropped start steps + the dead local `bots` insert) and THIN

## 0. Context & scope

herobids `apps/api/src/routes/blueprints.ts`, handler
`POST /blueprints/:blueprintId/instantiate`, the **BOT branch**, currently does a
local `tx.insert(bots)` (confirmed ~line 2277) inside the idempotency
`db.transaction`. That is a local trading write and must move over the Traderton
REST boundary so herobids holds NO trading writes.

**In scope:** the BOT branch only.
**Explicitly OUT of scope — DO NOT TOUCH:** the AGENT branch
(`createAgentFromPayload`, `bp.kind === 'agent'`) writes only platform tables and
is unaffected. `create_bot` in traderton is a copied parity surface
(create-AND-start, agent-scoped, self-generated id) and is left UNTOUCHED — we
author a NEW sibling tool instead.

### Settled design (from the decision authority — implement exactly; do not re-decide)
- Author a NEW traderton tool `instantiate_bot`: it reproduces the drive-target
  create path but OMITS the start steps (stopped-create = a DELETION of start,
  not new authoring).
- The tool accepts caller-supplied `actorId` + `venueAccountId` + `config` +
  lineage, persists `status:'stopped'`, `creatorType:'user'`,
  `creatorId`=subject user id; returns `{ botId, status:'stopped' }`. No
  `connectionId` (decision 13).
- herobids replaces `tx.insert(bots)` with a boundary call (Shape 1 seam),
  keeping the advisory lock + local idempotency/binding-validation reads;
  boundary FIRST, then local platform records on success.
- Idempotency: boundary dedups its own insert on the four-tuple; caller-supplied
  `actorId` makes a boundary-success/local-fail retry converge. The residual
  inert stopped-orphan divergence is an ACCEPTED bounded divergence (already
  logged in 003 + 001) — DO NOT build a reconciler (that is 010 backlog).

## Open Questions — RESOLVED by coordinator (grounded against real code, 2026-09-12)

**A-i — caller-supplied id + which persist primitive. RESOLVED.**
Read `BotRepository.tryCreateBotWithLimit` (repositories.ts ~1221): it (a) SELF-generates `id = crypto.randomUUID()`, (b) counts `status='running'` bots against `maxBots` and refuses when at cap, (c) inserts `status:'stopped'` with `ownerId/venueAccountId/config/creatorType/creatorId` — it has NO `blueprintId`/`blueprintRevisionId`/`configSnapshot` columns in its insert and NO caller-id param.
**Decisive parity fact:** the herobids SOURCE instantiate write was a PLAIN `tx.insert(bots)` with `status:'stopped'` — it did NOT go through `tryCreateBotWithLimit` and did NOT enforce the running-bot limit (instantiation creates a STOPPED bot; the limit is a RUNNING-slot limit enforced at start). So reproducing the source faithfully means instantiate_bot must NOT reuse `tryCreateBotWithLimit` (that primitive is coupled to the running-limit + self-id + no-lineage, which would DIVERGE from the source stopped-insert on all three counts).
**Ruling for the Implementer:** author a NEW thin repository method `BotRepository.insertStoppedBot({ id, ownerId, venueAccountId, config, creatorType, creatorId, blueprintId, blueprintRevisionId, configSnapshot })` that does a single `insert(bots).values({... status:'stopped', createdAt, updatedAt})` with the CALLER-SUPPLIED id and the lineage columns. This is a copy-faithful reproduction of the source `tx.insert(bots)` (same columns, minus the decision-13 connectionId), NOT authored trading logic — it is the extraction of the exact source insert behind a repo method. Do NOT extend `tryCreateBotWithLimit`. Confirm the traderton `bots` schema HAS `blueprintId`/`blueprintRevisionId`/`configSnapshot` columns (grep schema/bots.ts) — if any are absent, that is a schema gap to flag (the source persisted them), NOT to silently drop.
Correspondingly, the A1 drive-target step is NOT needed as a `createAndStart` fork — instantiate_bot's `execute` calls `insertStoppedBot` directly (it still runs the COPIED guards: execution-capability, BotConfigSchema parse, mode-escalation, swap-symbol — those are the trading-domain validations the source route ran; keep them). There is no start/mark/enqueue at all.

**A-ii — category / side-effecting classification. RESOLVED.**
`create_bot` is `category:'execute-trade'`. instantiate_bot drives NO executor (stopped-create) and is owner/venue-account scoped, so `'write-database'` is the faithful category (it PERSISTS but executes no trade) — provided `getCategoryOperation('write-database') !== 'read'` so it still routes through `dispatchSideEffecting`. Implementer: verify `getCategoryOperation` in the dispatcher maps `'write-database'` to a side-effecting op; if it does NOT, fall back to `'execute-trade'` (which is proven side-effecting). Either way it MUST be side-effecting (idempotent create is the whole point). Do NOT set a read category.

**A-iii — venue injection for a caller-specified venueAccountId. RESOLVED (design).**
create_bot resolves a per-owner DEFAULT venue account via the subject→injection resolver; instantiate_bot must honour a SPECIFIC caller-supplied `venueAccountId`. Since `insertStoppedBot` (A-i ruling) persists `venueAccountId` directly from the payload and the bot is STOPPED (no actor start → no venue/venueType injection needed for an executor), instantiate_bot does NOT require the bin.ts default-venue resolver at all: it takes `venueAccountId` in the payload, verifies it belongs to the owner (owner-scoped guard — mirror how owner-scoped tools verify ownership, e.g. a `getVenueAccountForOwner`-style check or the existing get_venue_account owner-narrow), and persists it. Implementer: confirm an owner-scoped venue-account ownership check exists (provisioning.ts `get_venue_account` is owner-narrowed) and reuse that guard so a caller cannot bind another owner's account. venue/venueType for the config stamp come from the payload config (as the source built botConfig with venue/venueType), NOT from a default resolver.

**C-i — boundary call inside vs outside the advisory-lock tx. RESOLVED.**
Do NOT hold the herobids `db.transaction` (which holds the pg advisory xact lock + a pinned connection) open across the REST round-trip. Restructure to: (1) a SHORT local tx (or the advisory lock) does the replay/conflict check + binding validation reads and RELEASES; (2) issue the boundary `instantiate_bot` call OUTSIDE any open tx; (3) on success, a SECOND short local tx writes the `blueprint_instantiation_requests` + `blueprint_usage_events` rows. The advisory lock's job is to serialize concurrent same-key requests; the idempotency GUARANTEE against duplicates is the local `blueprint_instantiation_requests` unique check PLUS the boundary's own four-tuple dedup (caller-supplied actorId makes a retry converge). Holding a connection across a 30s network call under a table/advisory lock is a real availability risk and is NOT what the source did (the source had no network call). Implementer: keep the advisory lock scoped to the local reads/writes; the boundary call sits between. If two concurrent same-key requests race, the second either sees the first's committed idempotency row (replay) or, if it beats the commit, the boundary's four-tuple dedup returns the same botId — no double insert. This is the Shape-1 seam done safely; note it in a code comment cross-referencing 003.
