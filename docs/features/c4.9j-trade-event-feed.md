# c4.9j — Trade-event feed: expose Traderton `journal_events` as a cross-owner polled read + re-point the herobids AlertDispatcher

**Status:** PLAN (not yet implemented)
**Repos / branches:** traderton `l3-integration` · herobids `consume-traderton`
**Law:** COPY, NEVER AUTHOR trading behaviour. The only authored things here are
DELETIONS (herobids' `new PgJournal(db)` reader) and THIN boundary SEAMS (three
read-only pass-through tools + a narrow `TradeEventFeed` port/adapter). No trading
logic is authored — the AlertDispatcher's KEEP internals are untouched.

---

## 0. Context & scope

Trading has been extracted from herobids into Traderton behind a REST boundary;
herobids holds NO trading reads. This slice preserves the herobids
`AlertDispatcher`'s Telegram alerting on Traderton-owned trade events — a **settled
Deferred-required-for-cutover parity obligation** — by exposing Traderton's
`journal_events` as a **cross-owner polled read** over the boundary and re-pointing
the AlertDispatcher onto it.

The AlertDispatcher (`herobids apps/worker/src/alerting/alert-dispatcher.ts`)
depends on `PgJournal` for EXACTLY three methods:
- `scanAfter(opts)` — the tick's cursor-based global scan.
- `getByIds(ids)` — `seedCooldownsFromDb` restart seeding.
- `getById(id)` — `retryPending` per-delivery event lookup.

**This slice makes those three reads cross the boundary. Nothing else moves.**

**KEEP (do NOT relocate — verified against the source):** the dispatch loop, the
Redis singleton lease (`lease:alert-dispatcher`, 30s TTL), the durable cursor
`{createdAt, seenIds}`, the cooldown map, `evaluateAlertPolicy`,
`AlertDeliveryRepository` (Telegram delivery records/dedup — herobids-local
platform tables), and `TelegramClient` sending. Only the `journal_events` READ
crosses.

**Event scope:** the feed serves Traderton-owned trade/lifecycle types only
(`risk.*` / `execution.failure` / `instance.*` / `stream.disconnect` /
`reconciliation.*`). herobids' alert policy passes `collectPrefixes()` as
`typePrefixes` and REMAINS the filter — the feed itself applies no owner/actor
narrowing (deliberate cross-owner; see §Authorization).

## Authorization (SETTLED-within-rules — noted, not re-decided)

These three tools are cross-owner (`scanAfter` deliberately applies no
owner/actor filter). They are invoked under a SYSTEM subject
(`actor.type='system'`, `id='alert-dispatcher'`) — the SAME established pattern as
herobids' existing `systemReadBoundary` (`market-intel`). The boundary enforces
scope INSIDE each tool body, not via the resolver; `ACTOR_TYPES` already includes
`'system'`, and for `read-database` the subject resolver short-circuits
(`skipVenueResolution`) so no owner-owned row is required.

The operator-config grant `allowedActorTypes: ['system']` on the
alert-dispatcher's consumer entry fences cross-owner access to that consumer.
**This consumer-config value is the human's routine operator-config touchpoint at
cutover — NOT a design gate.** (It is set in herobids' `boundary` operator config
for the consumer id the dispatcher's client uses.)

**OQ-2 (see Open Questions):** the ruling says "if a per-consumer allow-list of
tool names exists, restrict these 3 tools to the operator consumer." Grounding
against `packages/boundary/src/config.ts`: **no per-consumer tool-name allow-list
field exists** — `AllowedConsumerSchema` fences by `allowedActorTypes` only. So the
cross-owner tools cannot be tool-name-fenced with today's config surface. Flagged,
not invented.

## Risks
- **R1 (MED):** ISO↔Date round-trip fidelity. The cursor `{createdAt, seenIds}` is
  the correctness core of at-least-once scanning; `createdAt` must survive
  Date→ISO (outbound payload) and ISO→Date (inbound rows AND the re-parsed cursor
  in A1) without drift. Mirror `toJournalRow`'s proven rehydration. A B3/A5 test
  should pin this.
- **R2 (MED):** failure semantics. B3 MUST throw (not return `[]`) on
  failure/transport_error so the cursor does not falsely advance. Returning empty
  would silently drop events between ticks. Covered by B3 + a test.
- **R3 (LOW):** cross-owner exposure is intentional but wide; with no per-tool
  allow-list (OQ-2) the fence is actor-type only. Acceptable per the ruling
  (system subject + `allowedActorTypes:['system']`), but note it.
- **R4 (LOW):** dead-import removal in `index.ts` / `alert-dispatcher.ts` — gated
  by `tsc --noEmit` (`noUnusedLocals`).

## Open Questions (flagged against grounding — resolve before/with implementation)

- **OQ-1 — `ctx.db` in the boundary context for read tools. RESOLVED (grounded).**
  `packages/boundary/src/bin.ts` injects the raw Drizzle handle as `db` on every
  `TradingToolContext`. The existing `get_owner_bot_journal` /
  `get_agent_journal_events` tools already do `new PgJournal(ctx.db as Database)`.
  No blocker. (Listed for completeness per the routing instruction.)

- **OQ-2 — per-consumer tool-name allow-list to fence the cross-owner tools.
  OPEN (grounded: no such surface).** `AllowedConsumerSchema`
  (`packages/boundary/src/config.ts`) fences by `allowedActorTypes` ONLY — there is
  NO per-consumer tool-name allow-list field. So the ruling's "restrict these 3
  tools to the operator consumer" cannot be done with today's config. The fence is
  therefore actor-type only (`allowedActorTypes:['system']` on the dispatcher's
  consumer). Two dispositions for the decision authority:
  (a) accept actor-type-only fencing for this slice (matches the existing
  `market-intel` system-read precedent — no new tool cross-owner beyond what
  system consumers already reach), OR
  (b) ADD a per-consumer `allowedTools?: string[]` field to `AllowedConsumerSchema`
  + a dispatcher check (a NEW authored boundary rule — larger scope, likely a
  docs/010 later-option, and beyond COPY-never-author's "thin seam"). Do NOT
  invent (b) silently; flag for the human at the operator-config touchpoint.

- **OQ-3 — system subject resolves for a read tool. RESOLVED (grounded).** For
  `read-database`, `skipVenueResolution` is true, so `resolveSubjectInjection`
  returns a minimal injection without reading any owner-owned bot/venue-account
  row. A `system` actor with no owned entities resolves cleanly. No blocker.

- **OQ-4 — unconfigured-boundary degrade for the dispatcher.** The existing
  `systemReadBoundary` returns `undefined` when `baseUrl`/`hmacSecret` are absent
  (market-intel tools then degrade to a typed unavailable outcome). The
  AlertDispatcher has no such degrade path today (it took a concrete `PgJournal`).
  Decide with the coordinator: when the boundary is unconfigured, either (a) do
  not start the dispatcher (log a warning — it already warns-and-returns when
  Telegram is unconfigured, so a symmetric "feed unavailable" early return fits),
  or (b) inject a feed whose methods throw so the loop reschedules harmlessly.
  Prefer (a) — a symmetric config-guard early return, matching the dispatcher's
  existing `!this.telegram` warn-and-return. Not a blocker; a small wiring choice
  to confirm.
